 CryptPad - Reverse Engineering Writeup
================================================================================

Challenge : "We found this on an old machine. Can you decrypt it?"
Files     : cryptpad.exe, flag.enc
Author    : crudd
Category  : Reverse Engineering / Crypto
Format    : CMO{...}

FLAG: CMO{r0ll_y0ur_0wn_b4d_c0d3}

--------------------------------------------------------------------------------
TL;DR
--------------------------------------------------------------------------------
cryptpad.exe is a tiny 32-bit Windows GUI "encrypted notepad". Its self-
described "custom encryption algorythm" is really:

    ciphertext = pre_XOR(ks) -> RC4(key) -> post_XOR(ks)

The SAME keystream ks is XORed before and after RC4, so the two XOR layers
cancel (XOR is commutative/associative). The cipher reduces to plain RC4 with
an 8-byte key.

Worse: when the program saves a file it APPENDS the random RC4 key to the file
in a 13-byte trailer. So the key needed to decrypt sits inside flag.enc itself.
Recover the key from the trailer, run RC4, done.

--------------------------------------------------------------------------------
2. LOCATING THE CRYPTO
--------------------------------------------------------------------------------
0x4013bd   Save handler (alloc, CreateFileA, GetWindowTextA, encrypt, WriteFile)
0x4014eb   crypt(buf, n, dir)  - the cipher (encrypt dir=1, decrypt dir=0)
0x40166b   rng() wrapper around SystemFunction036 (RtlGenRandom)

2.1 Save handler (0x4013bd), reconstructed:

    len   = GetWindowTextLengthA(hEdit);
    N     = len + 1;                       // include NUL
    pad   = 0x40 - (N % 0x40);             // pad to multiple of 64
    total = N + pad;                       // == 64 here
    buf   = HeapAlloc(heap, 0, total);
    hFile = CreateFileA(name, GENERIC_WRITE, 0,0, CREATE_ALWAYS, NORMAL, 0);
    GetWindowTextA(hEdit, buf, N);         // note text + NUL into buf
    rng(buf + N, pad);                     // random padding
    rng(0x4024c5, 8);                      // generate 8-byte KEY
    crypt(buf, N, 1);                      // encrypt first N bytes
    WriteFile(hFile, buf, total, &written, 0);

Only the first N bytes (note + NUL) are encrypted. The rest is random padding,
plus a trailer written by crypt() (see 2.4).

2.2 Key generator (0x40166b):
    push [ebp+0xc]   ; length
    push [ebp+8]     ; buffer
    call SystemFunction036   ; RtlGenRandom(buf, len)
    The 8-byte key lives at 0x4024c5 in .data.

2.3 crypt(buf, n, dir) at 0x4014eb - three stages over n bytes, key @0x4024c5:

  Stage 1 - pre-XOR (0x40154a):  buf[i] ^= ks[i]
            ks[i] = byte at (0x4024c5 + i)
            (key index resets every 8, but edi keeps walking - irrelevant, see 3)

  Stage 2 - RC4 (0x40156f .. 0x40160a):
     0x40156f  S-box identity init at 0x403795:  S[i] = i
     0x401583  key schedule at 0x403695 repeating the key: ksched[i] = key[i % 8]
     0x4015a3  RC4 KSA (standard):
                 j=0; for i in 0..255: j=(j+S[i]+ksched[i])&0xff; swap(S[i],S[j])
     0x4015d0  RC4 PRGA (standard, i starts at 1):
                 i=j=0
                 for k in 0..n-1:
                     i=(i+1)&0xff; j=(j+S[i])&0xff; swap(S[i],S[j])
                     buf[k] ^= S[(S[i]+S[j])&0xff]

  Stage 3 - post-XOR (0x40160c): identical to Stage 1, same ks.

2.4 Trailer writer (0x401631, only when dir==1):
    p = buf + N + pad - 13;     // 13 bytes before end of the 64-byte block
    *(uint32*)p = N;            // store N (len+1)
    memcpy(p+4, 0x4024c5, 8);   // store the 8-byte KEY
    p[12] = 0x08;               // marker

  => the LAST 13 BYTES of every saved file are:
       [ uint32 N ][ 8-byte RC4 key ][ 0x08 ]

--------------------------------------------------------------------------------
3. THE TWO FATAL WEAKNESSES
--------------------------------------------------------------------------------
(1) The XOR layers cancel.
    Output = P ^ ks ^ RC4ks ^ ks. XOR is commutative, the ks terms cancel,
    leaving P ^ RC4ks. The "custom" cipher is just RC4 with the 8-byte key.
    (The buggy non-resetting pre/post XOR keystream is completely irrelevant.)

(2) The key is stored with the ciphertext.
    The trailer embeds the random RC4 key in plaintext. No brute force and no
    known-plaintext gymnastics needed.

--------------------------------------------------------------------------------
4. RECOVERING THE KEY FROM flag.enc
--------------------------------------------------------------------------------
Last 13 bytes (offsets 51-63):
    1c 00 00 00 | e8 17 1b f4 50 3f 3d 70 | 08

    N      = 0x0000001c = 28   (note text = 27 chars + NUL)
    key    = e8 17 1b f4 50 3f 3d 70
    marker = 0x08  (OK)

Only the first 28 bytes are RC4 ciphertext; bytes 28-50 are random padding;
bytes 51-63 are the trailer.

--------------------------------------------------------------------------------
5. DECRYPTION / POC  (solve.py)
--------------------------------------------------------------------------------
    #!/usr/bin/env python3
    def rc4(key, data):
        S = list(range(256)); j = 0
        for i in range(256):
            j = (j + S[i] + key[i % len(key)]) & 0xff
            S[i], S[j] = S[j], S[i]
        out = bytearray(); i = j = 0
        for b in data:
            i = (i + 1) & 0xff
            j = (j + S[i]) & 0xff
            S[i], S[j] = S[j], S[i]
            out.append(b ^ S[(S[i] + S[j]) & 0xff])
        return bytes(out)

    ct = open("flag.enc", "rb").read()
    N   = int.from_bytes(ct[-13:-9], "little")   # 28
    key = ct[-9:-1]                               # e8171bf4503f3d70
    assert ct[-1] == 0x08
    pt = rc4(key, ct[:N])
    print("N   =", N)
    print("key =", key.hex())
    print("flag=", pt.split(b"\x00")[0].decode())

Run:
    $ python solve.py
    N   = 28
    key = e8171bf4503f3d70
    flag= CMO{r0ll_y0ur_0wn_b4d_c0d3}

Verification: decrypted bytes are CMO{r0ll_y0ur_0wn_b4d_c0d3}\x00 - exactly
N=28 bytes (27 printable + NUL), matching CMO{...}.  OK.

--------------------------------------------------------------------------------
6. FULL REPRODUCTION STEPS
--------------------------------------------------------------------------------
1. unzip cryptpad_handout.zip            -> cryptpad.exe, flag.enc
2. file cryptpad.exe                      -> PE32 (x86) GUI
   strings -n 5 cryptpad.exe              -> "custom encryption algorythm", SystemFunction036
3. Disassemble (Ghidra / IDA / radare2 / objdump / capstone). Locate:
     Save handler 0x4013bd, crypt() 0x4014eb, rng() 0x40166b
4. Read algorithm: pre-XOR + RC4 + post-XOR (XOR layers cancel),
   trailer layout [N][key][0x08]
5. Pull key from last 13 bytes of flag.enc: N=28, key=e8171bf4503f3d70
6. RC4-decrypt the first 28 bytes -> CMO{r0ll_y0ur_0wn_b4d_c0d3}
7. Verify length (N), NUL terminator, and flag format

--------------------------------------------------------------------------------
7. TOOLS USED
--------------------------------------------------------------------------------
unzip / Expand-Archive  - extract the handout
file / magic bytes      - identify PE32 (x86)
strings                 - quick triage (cipher hint + imports)
pefile (Python)         - parse PE header, sections, imports, RVA->offset
capstone (Python)       - linear + targeted recursive x86 disassembly
Ghidra / IDA / radare2  - equivalent alternative static analysis
Python 3                - reimplement RC4 and decrypt
xxd / hex view          - inspect flag.enc trailer

Note: the binary uses SystemFunction036 (RtlGenRandom), so the key differs every
save - but since it is stored in the trailer, that randomness gives no security.

--------------------------------------------------------------------------------
8. KEY TAKEAWAYS
--------------------------------------------------------------------------------
* Don't roll your own crypto. Sandwiching RC4 between two identical XOR passes
  adds zero security - the layers cancel algebraically.
* Never store the key next to the ciphertext. A random per-file key written into
  the file trailer is no better than no key at all.
* For RE crypto: recover and READ the algorithm; exploit stored key material /
  known plaintext / structure; cap blind brute force. Here the binary literally
  hands you the key.
